# 飞书技术文档 · 可读性原则（可复用规范）

> **这是唯一权威副本（single source of truth）。** 两个姊妹 skill 共用它：
> - `gh-lark-tech-doc-writing`（写）—— 落笔时照它组织正文。
> - `gh-lark-comment-doc-editing`（改）—— 按评论就地改时，照它判断「改哪里 / 改成什么」；
>   额外约束：任何改动都要**保留其它评论的 quote 锚点**（就地改，不整段删重写）。
>
> 修改本文件即两边同时生效——请只改这一份，不要在各 SKILL.md 里另抄一份。

技术文档是给**决策/评审**看的，不是源码注释。目标：结论清楚、能扫读、没读过源码的
reviewer 也能看懂。

## 开篇命名必须与内容匹配，并先冻结关键术语
技术方案的首章标题必须准确描述该章承担的作用。背景、目标、范围不能笼统命名为“结论”；
只有已经完成论证、可供评审直接拍板的内容才能使用“结论”。落笔前先判断首章属于
“背景与目标”“方案概述”还是“结论与决策”，禁止沿用与正文内容不匹配的模板标题。

当正文反复出现内部仓库、服务、Agent、配置项或流程阶段时，在文档标题后、正文展开前提供一张
紧凑的两列术语表，表头固定为“名词 / 本文含义”。每个概念只保留一个统一名称并用一句话
解释职责或来源；后文正文、表格和画板必须全部使用同一名称，禁止同一对象混用简称、旧称和泛化称呼
。首次确定统一名称后，全文不再切换到历史名称或临时简称。

交付前必须完成两项扫描：

- 检查所有章节标题是否与章节内容一致，尤其不能把背景、目标或范围误标为“结论”。
- 建立全文术语表，搜索每个统一名称的常见别名；正文、表格、图题和画板节点必须同步
  收敛，不能只改正文而遗漏图内文字。

正文默认使用中文。只有代码标识、配置键、仓库名、产品正式名称或没有稳定中文译名的行业术语
保留英文；普通流程概念和状态必须使用中文，不能用 `revision`、`mechanism`、`plan` 等英文替代
“版本”“机制”“计划”。术语表、正文、表格和画板执行同一口径。

只描述最终采用的方案及其必要边界。已经移除、未采用或本期不建设的能力，不得以“本期不做”
“不设置某阶段”“不是某服务”等否定句写入正文或画板；若某项不是执行链路的一部分，直接删除，
不要为了说明它不存在而再次引入该概念。交付前扫描“不做 / 不设置 / 不建设 / 不是 / 非”等
否定式范围表述，保留真正的安全约束，删除对未采用方案的解释。

## 面向人的理解过程组织全文
技术文档不是模块说明书。先确定 reviewer 会按什么顺序形成判断，再按这个过程组织章节。技术方案
默认遵循以下阅读路径：

1. 先看结论、目标与方案选择，知道为什么这样做。
2. 再看一张端到端流程图，建立完整心智模型。
3. 沿执行顺序逐阶段展开输入、动作、产物和失败行为。
4. 最后看异常与回滚、成熟度边界和验收标准。

不要先按存储、配置、服务、脚本等模块各写一章，再让读者自行拼接流程。模块职责应放进它实际参与
的流程阶段；只有模块本身存在独立接口契约或生命周期时，才单独成章。

表达形式遵循：

- **图形优于纯文本流程**：出现三个及以上连续步骤、跨模块传递、条件分支或对象关系时，先根据
  信息语义选择流程图、时序图、拓扑图、漏斗图或泳道图；正文只解释图中无法表达的决策和边界，
  不再逐句复述流程。
- **列表优于大段并列文字**：同层级的职责、输入、产物、约束和风险拆成列表，一条只讲一件事。
- **段落保留给论证**：背景、原因、取舍和结论仍使用有承接关系的段落，不把所有正文机械列表化。
- **阶段标题使用动作或结果**：优先写“生成并发布产物”“运行时下载并装载”，避免只写模块或
  基础设施名称。

## 正文必须无状态
技术方案正文必须脱离讨论过程独立成立。不要写“本方案合并了两份方案”“沿用上一版”“基于本轮
讨论”“现有 PoC / 实验分支证明”等只有参与者才理解的过程性背景，也不要先列未定义的候选方案再
直接进入对比。正文直接说明业务或技术背景、要解决的问题、最终设计和约束；调研文档、历史方案与
代码分支只放在“参考依据”或实施附录中，不参与主结论的论证。

交付前扫描“既有设计 / 上一版 / 同上 / 当前不是从零 / PoC / 实验分支 / 参考方案”等表达：
删除纯过程描述；若其中包含必须保留的事实，将事实改写成不依赖历史上下文的设计约束。

## 结论优先，去问答体
对于**已确认结论**的问题，去掉「问题？→ 已确认：答案」的问答形式，**直接给确定性结论**
（例：写成「现有监控事件已覆盖关键指标」而非保留原问句）。
（改场景）已确认项甚至可从「待确认表」中整行移除。

## 只留方案所需结论，砍掉无关实现细节
一段里**第一句往往就是本方案需要的结论**，后面堆的源码行号、内部函数名和调用链等实现细节，
与当前决策无关时应删除。判据：删掉某句后，reviewer 对方案的理解不受影响，就只保留结论。

## 拆密集长段（一段一事）
一个 `<p>`/`<li>` 里塞进多类并列信息（多个成因、多条配置、多个来源）→ 阅读者要在长句里
自己切分。**拆成带 ①②③ 标号或多条 `<li>` 的独立条目**，一条只讲一件事。判据：单块正文
（去标签后）超过 ~200 字且含 ≥3 个 `；`/并列分句，就该拆。（改场景）用 `block_replace`
把一个块换成多个块即可（会顺带让原锚点评论成孤儿——若该块正是被要求重写的评论锚点，这是
预期结果）。

## 大段无格式文本 → 带小标题的列表
一整块没有任何格式的长文本（错误码 + 动作 + 边界 + 文案糊在一句里）极难扫读 → 拆成
**多条 `<li>`，每条一个 `<b>小标题</b>：内容`**（如「错误码 / 拒绝动作 / 对调用方透明 /
文案」）。与「拆密集长段」互补：那条侧重按并列项切分，这条侧重给每项加语义标题。

## 方案对比 → 候选方案列表 + 紧凑选型表
技术方案需要比较多个候选方案时，使用固定的「方案选择」结构：

1. 用一句话引出候选方案。
2. 用无序列表分别说明各方案，一条对应一个方案。
3. 用一句话点明方案间真正影响选型的核心差异。
4. 使用三列表格完成对比：列为「对比项 / 方案一 / 方案二（推荐 ✅）」；行只保留
   「方案说明 / 优点 / 缺点」。

表格内遵循以下规则：

- **推荐项直接标在方案表头**，让 reviewer 扫一眼即可识别结论。
- **方案说明突出关键机制**，可加粗决定该方案工作方式的核心动作或依赖关系。
- **优点和缺点使用无序列表**，一条只写一个实质影响；只保留会影响选型的差异，不补无关维度，
  也不要求两个方案的条目数量对称。
- **避免大型维度表**。不按发布、回滚、性能、依赖、风险等十余个维度逐行展开；这些信息归并到
  优点或缺点中表达。

推荐结构示例：

```xml
<p>当前有两种可选方案：</p>
<ul>
  <li>方案一：……</li>
  <li>方案二：……</li>
</ul>
<p>两种方案的核心差异是……</p>
<table>
  <thead>
    <tr><th>对比项</th><th>方案一</th><th>方案二（推荐 ✅）</th></tr>
  </thead>
  <tbody>
    <tr><td>方案说明</td><td>……</td><td>……</td></tr>
    <tr>
      <td>优点</td>
      <td><ul><li>……</li></ul></td>
      <td><ul><li>……</li><li>……</li></ul></td>
    </tr>
    <tr>
      <td>缺点</td>
      <td><ul><li>……</li><li>……</li></ul></td>
      <td><ul><li>……</li></ul></td>
    </tr>
  </tbody>
</table>
```

## 多模块职责分工 → 按角色拆条，一角色一条
描述**多个模块/角色/端各自负责什么**（谁做 A、谁做 B）时，别用一句 prose 把所有角色的
职责串起来——读者要在长句里自己切分「哪句是谁的活」。改成**按角色拆成列表，每个角色一条，
`<b>角色名</b>：它负责的职责（多项用「；」并列）`**。判据：句子里出现 ≥2 个主语切换
（「node 负责…，Go 负责…」「A 端…，B 端…」），就该拆。

当一句话同时出现 ≥3 个仓库、服务、配置或 Agent 名称时，必须改成列表或职责表；即使这句话是
摘要或结论，也不能用逗号串联多个角色职责。交付前扫描所有同时包含多个模块名和“负责 / 维护 /
发布 / 消费 / 注入”等动作的段落，确认已完成拆分。

Before（一句串起两端职责，难分谁做什么）：
> 客户端收集输入并发起请求，服务端校验输入并返回处理结果。

After（按角色拆条，各角色职责一目了然）：
```xml
<p>架构概述：</p>
<li><b>客户端</b>：收集输入并发起请求。</li>
<li><b>服务端</b>：校验输入并返回处理结果。</li>
```
（改场景）用 `block_replace` 把原 prose 块换成「一个概述 `<p>` + N 条角色 `<li>`」即可。

## 引入新概念先一句话解释来源（强制）
正文首次出现**内部专有名词 / 机制 / 函数 / 配置项**（尤其自研、非通用的）时，紧跟一句话
说明它是什么、从哪来，用括注最省事。目的：让没读过源码的 reviewer 也能看懂。说明应包含对象
类别、维护方和用途，例如“现有配置项，由运行时维护，用于选择执行策略”。

只在**首次**出现处解释，后文复用不再重复。

## 根据关系语义选择图形，而非统一套流程图
图形先回答问题，再决定样式：对象关系用拓扑图，多参与方交互用时序图，门禁收敛用漏斗图，
条件与异常路径用决策流程图，跨角色端到端过程用泳道图。多张图分别独立选型，不为了统一视觉而
复用同一模板。

判据：句子里出现 ≥2 个「之后/之前/时/则/否则」等顺序或分支词，或出现 ≥3 个互相关联对象时，
优先画图。正文只保留一句话概述和图中无法表达的边界，不逐句复述图。具体画板工作流以
`gh-lark-tech-doc-writing/references/diagram-workflow.md` 为准。

工具不限定：规则图（时序 / 类 / 饼 / 甘特）Mermaid 写得快就用 Mermaid；总览图 / 架构图 /
需要排版配色的示意图，Mermaid 常常又挤又丑 → 优先用自包含 SVG（`<whiteboard type="svg">…</whiteboard>`
或 `path="@abs.svg"`），能精确控制布局、圆角、分层底色、字号。Mermaid 不是硬性要求，
别为了「用 Mermaid」牺牲可读性和美观。

## 重构旧方案时逐图继承，禁止架构信息退化为文字
基于旧方案、参考文档或历史版本重写技术方案时，写入前必须盘点其中全部画板、图片和架构关系，
对每张图标记为「直接复用 / 按新契约重画 / 明确退役」。原图字段或目录失效时，只能淘汰旧实现，
不能连同它回答的架构问题一起删除；如果该问题在新方案中仍成立，就按最终契约重画。

当方案同时存在以下信息时，应分别画图，不得压成一张超大图后再用长文字补充：

- 组件和事实源之间的关系 → 总体架构或拓扑图。
- 多参与方交互顺序 → 时序图。
- 创建 / 修改 / 恢复 / 失败等条件分支 → 决策流程图。
- 候选输入到稳定产物的收敛过程 → 漏斗图或准入流程图。

交付前做视觉密度检查：若一个章节包含三个以上连续步骤、三个以上互相关联对象，或超过一屏的
流程性文字，先补对应画板；画板完成后删除被图覆盖的职责表、步骤列表和流程复述，只保留契约、
边界和图中无法表达的精确字段。

## 图画好后，删掉被它覆盖的文字/伪代码
一段流程已用图（架构图 / 时序图）讲清后，正文里描述同一流程的 **bullet 列表、纯流程伪代码**
就成了重复噪声 → 删掉，只留一句概述引出图。**判据看伪代码性质**：
- **接口契约类**（如参数定义、类型定义、对外方法签名）→ **保留**，图表达不了精确签名。
- **纯流程 / 时序类**（「先 A 再 B，命中 C 则 D」串起来的伪代码）→ 被图覆盖后**删除**，别图文各写一遍。

## callout 样式随状态降级
callout 的**颜色/emoji 是状态信号**，不只是装饰。当评论确认一个阻塞点已经解除、只剩后续风险时，
正文的 callout 要**同步降级**，否则 reviewer 会被过期的红色误导：
- 红 ❗（阻塞 / 需对齐 / 必须解决）→ 灰 📝（提示 / 已知风险 / 后续处理）。
- 降级时正文仍保留该评论的 quote 锚点子串（就地 `block_replace` 整块换掉，别删段重写）。

## 时序图要标激活时机，改动配色仅用于显式对比
画**多模块交互时序图**（Mermaid `sequenceDiagram`）时，光画消息箭头不够，还要让 reviewer 一眼看清
「谁在什么时候被激活、这次到底改了哪些环节」：

1. **标激活时机（activation）**：每个 participant 被调用到返回的生命周期，用
   `activate <P>` / `deactivate <P>` 包起来（或消息用 `->>` 触发、`-->>` 返回），让「模块何时上场、
   何时下场」在图上可见，而不是只有一串平铺的箭头。
2. **按改动性质配色**：仅当用户明确要求比较现状与目标、复用与改造时，才用
   `rect rgb(r,g,b)` 把相关消息段框起来并配色区分——
   **绿色（如 `rgb(216,243,220)`）= 本次新增**、**黄色（如 `rgb(255,242,204)`）= 本次改造**、
   **无底色 = 复用现状**。并在图顶用一条 `Note over <首>,<尾>: 图例 绿色=新增 / 黄色=改造 / 无底色=复用现状`
   写明图例。目的：reviewer 不用逐条读消息就知道「这次动了哪里、是加还是改」。
3. 消息文案里也可加「新增 / 改造」前缀（如 `A->>B: 新增参数校验`），与底色互为冗余提示。

若整篇描述的是一套新方案，画板只呈现最终链路，禁止添加“新增 / 改造 / 复用现状”图例、配色或
文字标签。激活标记仍按参与方生命周期保留。
