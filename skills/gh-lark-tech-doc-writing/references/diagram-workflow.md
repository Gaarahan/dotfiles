# 技术文档画板工作流

## 1. 先确定每张图要回答的问题

先建立图表清单，每张图只回答一个核心问题。根据关系语义选型：

| 要回答的问题 | 首选图形 | 典型内容 |
|---|---|---|
| 对象之间是什么关系 | 拓扑图 / 架构图 | 组件、资源、实例、上下游依赖 |
| 多个参与方按什么顺序交互 | 时序图 | 调用方、服务、存储、运行时 |
| 输入如何经过门禁逐步收敛 | 漏斗图 | 候选输入、校验、准入、稳定产物 |
| 条件如何决定路径，异常如何旁路 | 决策流程图 | 绑定、缓存、校验、失败处理 |
| 多角色如何完成端到端过程 | 泳道图 | 代码仓库、发布组件、依赖服务、运行时 |
| 候选方案有什么取舍 | 紧凑表格 | 方案说明、优点、缺点；通常不画图 |

多张图分别独立选型。不要为了视觉统一，把拓扑、门禁、时序和决策都画成相同的卡片流水线。

## 2. 选择飞书画板实现路径

使用 `lark-whiteboard` 和 `lark-whiteboard-cli`，并遵循它们的格式路由：

- 时序图、思维导图、类图、饼图、甘特图：优先 Mermaid。
- 架构图、拓扑图、漏斗图、泳道图、复杂流程图：优先 DSL，以控制布局、层级和连线。
- 文档最终产物必须是飞书原生可编辑画板。PNG/JPG 仅用于本地或线上回读，不得替代画板写入。
- 每张图使用独立产物目录和唯一幂等 token，避免多图之间复用节点 ID 或中间文件。

## 3. 先预览，再写回

对每张图执行：

1. 生成 Mermaid 或 DSL 源文件。
2. 渲染本地预览。
3. 检查信息完整、文字无截断、连线无交叉、图层顺序正确、画布比例适合文档阅读。
4. 对已有画板先执行覆盖 dry-run；按 `lark-whiteboard` 的授权规则确认后写回。

图层规则：背景和连线先定义，节点后定义；需要覆盖在节点上的文字或标注最后定义。能把文字内嵌到
原生形状时优先内嵌，减少独立文字层被容器遮挡的风险。

## 4. 逐张线上回读

写回后必须用 `whiteboard +query --output_as image` 导出线上实际渲染结果，逐张检查：

- 是否出现空白画板或内容过小，导致默认视口看起来为空白。
- 容器、背景或后写入节点是否遮住文字和连线。
- 标题、节点文字、判断菱形和连线标签是否裁切或重叠。
- 连线是否穿过节点，异常旁路是否压住主链路。
- 画布是否过高、过宽或留白过大，影响文档内阅读。

本地预览通过不等于完成；只有线上回读通过才算交付。如果文档包含多张画板，应先从文档结构提取
全部 token，再逐张导出，不能只抽查最后修改的一张。

## 5. 批量更新边界

- 用户要求“先生成一个看看”时，只创建或更新一张代表性图，等待用户确认视觉方向。
- 用户确认后再批量更新剩余画板；每张图仍需独立选型和独立验收。
- 发现某张图失败时，只修复该图，不覆盖已经验收通过的其它画板。
